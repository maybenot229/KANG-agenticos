## Context

ADR-046 built real, persisted `conversation`/`message` storage and explicitly left retention unbuilt, naming it "memory_steward's own future mechanical work." Investigating that claim rather than assuming it, three things ground this ADR:

1. **The purge mechanism is already fully specified**, not invented here. `07_DATABASE.md`'s own DDL comment on `conversation.purged` says exactly what "purge" means: delete the `message` rows (the transcript), keep the `conversation` row with `purged=1` so its id survives for `06_MEMORY §9.1`'s future `from_conversation` link. `memory.toml`'s `[retention] conversation_days = 90` already names the threshold. Nothing about *what* to build is open.
2. **What genuinely is open: which principal runs it.** `05_AGENTS` Appendix E already reserves a job slot for this shape of work — `memory_steward.nightly` ("daily, Sleeping, run_once_latest") — but that slot has never been registered in `scheduler_wiring.py` (no `JOB_OPERATIONS` entry, no `Job` row, nothing in `AGENT_ROUTED_JOBS`). `memory_steward.toml`'s own header says plainly: "no executor runs this agent yet." Its declared `tools` (`gate.client`, `notify:digest`) are illustrative prose, not resolved operations (same gap ADR-041 corrected for `deadline_sweep`) — because its *real* mandate (janitor/dedup/consolidation over memory records) depends on the memory store and gate, neither of which exists yet (Phase 2, not started — confirmed against the Build State note's own M7 position: Phase 1 is still in progress).
3. **Conversation purge does not share that Phase-2 dependency.** `06_MEMORY §1.3` and §7.1 both label conversation transcripts **non-memory** explicitly — they live in `ConversationStore` (ADR-046), never the memory store, never behind the write gate. Purging them needs nothing Phase 2 would add. This is a real, narrow, Phase-1-buildable slice, the same shape `chat` itself took as "the one Phase 1 does not postpone" while the rest of the cognitive roster stayed dormant (ADR-044).

**The fork this surfaces:** should this job's real trigger run through `memory_steward`'s mechanical-agent envelope (ADR-043/045's own pattern — a named agent, a new resolved tool, a new scope under `agent:memory_steward`), giving `memory_steward` its first real capability years ahead of the rest of its mandate — or should it run as a direct `kernel:scheduler` dispatch, the same shape `held_action_expire` already takes precisely because *that* job "names no agent in Appendix A's catalog at all"? `memory_steward` **does** have a catalog entry and **does** have this exact job slot reserved in Appendix E — the `held_action_expire` precedent for bypassing the envelope doesn't cleanly apply. But giving an agent its first live tool while 95% of its declared mandate stays fictional is a new shape this session hasn't tried, and worth deciding in daylight rather than defaulting.

**A second, smaller thing resolved here rather than silently assumed:** §7.1's "explicit saves extracted first" qualifier has no mechanism to hang off yet — there is no save/extraction flow (that's `from_conversation`, Phase 2). This slice's purge is therefore unconditional: every message in a conversation whose `last_message` is older than the threshold gets purged, full stop. The extraction exemption is a real, named future addition to this same job, not a gap silently ignored.

## Options

**A — Direct `kernel:scheduler` dispatch**, mirroring `held_action_expire`/`morning_plan`. New operation `conversation.purge`, new scope `conversations.purge` granted to `kernel:scheduler` alongside its existing `tasks.write`/`held_actions.expire`. No agent envelope, no change to `memory_steward.toml`. Simplest; defers "does `memory_steward` do anything real yet" until its actual Phase-2 mandate arrives as one coherent slice instead of piecemeal.

**B — Route through `memory_steward`'s mechanical-agent envelope**, matching ADR-043/045's pattern exactly: new operation `conversation.purge`, `memory_steward.toml`'s `tools` corrected from illustrative (`gate.client`, `notify:digest`) to real (`["conversation.purge"]`) — the same correction ADR-041/045 made for `deadline_sweep`/`backup_monitor` — new grant `"agent:memory_steward" = ["conversations.purge"]`. Matches Appendix E's own reserved slot (`memory_steward.nightly`) and gives `05_AGENTS`'s AG-004 unification goal ("everything KANG does autonomously is inspectable the same way") one more real instance. Honest downside: `memory_steward`'s catalog row still *describes* janitor/dedup/consolidation/pattern-extraction — none of that is true yet — so its agent definition would carry one real tool and two still-illustrative ones side by side, which needs saying plainly in the definition's own header, not smoothed over.

**Recommendation: B.** Appendix E already named this exact slot for this exact agent; Option A would mean inventing a *second* place (`kernel:scheduler`) for work the constitution already assigned a home, purely to avoid saying "`memory_steward` does one real thing before it does all of them" — which chat already established as an acceptable shape for exactly this kind of Phase-1/Phase-later split.

## Decision

### D1 — New `ConversationStore` port method: `purge_stale(cutoff: str) -> tuple[str, ...]`

Deletes every `message` row belonging to a conversation whose `last_message < cutoff` and `purged = 0`, sets that conversation's own `purged = 1` (id kept, transcript gone — exactly `07_DATABASE.md`'s own DDL comment), and returns the purged conversation ids. One transaction. Implemented for real in `SqliteConversationStore`; mirrored in `FakeConversationStore`; both proven by the same extended `ConversationStoreContract` (13 §2.3 — a fake that lies is a red build).

### D2 — New operation `conversation.purge`

`kind="command"`, `scope="conversations.purge"`, `idempotent=True` (re-running against the same cutoff purges nothing new — genuinely idempotent, not merely idempotency-keyed). Response: `{"purged": [ids...], "count": n}`, mirroring `deadline.sweep`'s own `{"alerted": [...], "count": n}` shape. The handler computes `cutoff = clock.now() - CONVERSATION_RETENTION_DAYS days` itself — `CONVERSATION_RETENTION_DAYS = 90` is a plain module constant in `api/operations/conversation_ops.py`, **not** read from `memory.toml`, because `config/defaults/memory.toml` does not exist yet (Phase 2 hasn't started — confirmed, not assumed). The constant cites `06_MEMORY §7.1`/Appendix A's own documented `90` directly, the same honest-hardcode shape `scheduler_wiring.py`'s own `TICK_INTERVAL_S` already uses ("a plain constant, not a kang.toml key — nothing has asked to tune this yet"). When `memory.toml` is built for real (Phase 2), this constant becomes that file's first real consumer — named here, not solved here.

**Unconditional this slice, and said plainly:** `06_MEMORY §7.1`'s "explicit saves extracted first" qualifier has no mechanism to hang off — `from_conversation` extraction is Phase 2. Every message past the cutoff is purged, full stop; the extraction exemption is future work on this same job, not a gap silently dropped.

### D3 — `memory_steward.toml`'s `tools` gains its first real entry, alongside two still-illustrative ones

`tools = ["conversation.purge", "gate.client", "notify:digest"]` — the first entry now resolves to a real, registered operation (checked by `run_mechanical_agent`'s `operation in agent.tools` allowlist, AG-005); the other two remain exactly what they always were, illustrative prose transcribed from Appendix A, structurally valid but not yet resolved (AG-005 explicitly defers this — "a future executor slice not yet decided," `tests/suites/CLAIMS.md`'s own words for `critic`/`planner`/etc.). A dated header comment says this plainly, the same honesty ADR-041/045's full corrections modeled, applied here to a partial one instead — because unlike `deadline_sweep`/`backup_monitor`, `memory_steward`'s full mandate (janitor/dedup/consolidation/pattern-extraction) genuinely isn't real yet, and pretending otherwise by silently dropping the other two would overstate what this ADR builds.

### D4 — New scope `conversations.purge`, granted to `agent:memory_steward`

`config/defaults/permissions.toml`: new grant `"agent:memory_steward" = ["conversations.purge"]` — this agent's first real grant, mirroring `agent:deadline_sweep`/`agent:backup_monitor`'s own single-purpose grants. No pairing-lint conflict: `memory_steward`'s own `AgentDefinition.scopes` field (the pairing-linted one, `memory.propose:lesson/preference/observation`) is untouched — `conversations.purge` is a `permissions.toml`-only grant for the new job's real caller, the same split `deadline_sweep`/`backup_monitor` already have (their own `scopes = []` in the `.toml`, their real grant living only in `permissions.toml`).

### D5 — New job `conversation_purge`, routed through the mechanical-agent envelope

`scheduler_wiring.py`: `CONVERSATION_PURGE_JOB = "conversation_purge"`; registered `schedule="daily"`, `catch_up="run_once_latest"` (Appendix E's own `memory_steward.nightly` row — daily, run_once_latest — this is that slot, filled for real for the first time); `JOB_OPERATIONS["conversation_purge"] = "conversation.purge"`; `AGENT_ROUTED_JOBS["conversation_purge"] = "memory_steward"`. `composition.py` wires `"conversation.purge": make_conversation_purge_handler(w.conversations, w.clock)` into the same handler table `deadline.sweep`/`chat.send` already sit in, reusing the existing `Core.conversations`/`Core.agent_registry` (ADR-046/043) — no new dependency wiring needed at the `Core` level.

## Consequences

- **`memory_steward` leaves "correct but entirely inert" for the first time**, years ahead of its declared Phase-2 mandate — a deliberate, named partial resolution, not a claim that janitor/dedup/consolidation now work. `kang explain` for `conversation.purge` invocations will show principal `agent:memory_steward`, same inspectability guarantee ADR-043/044/045 each extended.
- **A precedent for "give an agent one real slice of a much bigger mandate,"** distinct from ADR-043/045's "the whole mandate resolves to one/few real ops" shape. Chat already established Phase-1-slice-of-a-later-agent as acceptable (ADR-044); this is the first *mechanical* agent to take that same shape. Worth remembering before the next memory_steward ask (real janitor/dedup, Phase 2) — that work extends this agent's tools further, it does not replace them.
- **A real, honest hardcode**: `CONVERSATION_RETENTION_DAYS = 90` lives in code, not config, until `memory.toml` is real. Anyone tuning retention before Phase 2 edits code and redeploys — a real limitation, stated, not hidden behind a config file that doesn't back anything yet.
- **The "explicit saves extracted first" exemption is not built.** Every conversation past 90 days purges unconditionally. A future session building `from_conversation` extraction (Phase 2) must revisit this job, not treat today's unconditional purge as the final word.
- **`conversation.purge`'s `count` in its response can be legitimately zero** most nights (nothing yet is 90 days old) — this is a normal, healthy outcome, not a failure signal, the same way `deadline.sweep`'s `alerted: []` is normal on most hourly ticks.
