## Context

04_ARCHITECTURE §20.1 has carried this open question since the constitution was written: *"Embedding model choice (local-first candidate vs. API quality) — needs a small evaluation on Kang's real vault before v0.2. **Decision by benchmark, not vibes.**"* 18 §10 step 21 schedules the spike; IM-005 requires its output to be a decision rather than code. The spike ran on 2026-09-24 against the real vault, produced a findings document with zero vault content, and deliberately wrote no ADR. This is that ADR.

**What the spike established, and it is not what it set out to establish.** Six candidates were attempted; five completed. At n = 33 proxy queries the 95% confidence interval on recall@1 is roughly ±15 percentage points, while the entire observed spread across all five candidates is 12.2 points. The spike states the consequence itself rather than ranking anyway: *"Read the quality columns as 'statistically indistinguishable at this vault size,' not as a ranking."* That is the single most important thing it found — **the benchmark 04 §20.1 asked for cannot, at this vault's current size, distinguish these models on quality.**

So the decision cannot be made on measured quality, because there is none to speak of. It falls to the constraints that *are* settled, and two of them are decisive:

**Finding 1 — the runtime split is not a detail, it is the dependency question.** The spike's own table records which backend each candidate ran on: `nomic-embed-text` (768), `all-MiniLM-L6-v2` (384) and `bge-m3` (1024) via **Ollama**; `bge-base-en-v1.5` and `multilingual-e5-base` (both 768) via **sentence-transformers**, which pulled PyTorch in as a dependency. 17 §9 rules that local model weights are "not KANG's to store" and belong to the model runtime; 11 §25/E10 requires a written justification for any new dependency. A sentence-transformers candidate would put a multi-gigabyte ML stack inside KANG's own environment to do a job an already-installed external runtime does over HTTP. That removes two of the five candidates on architectural grounds, before quality is considered at all.

**Finding 2 — DB-004 already rejected 384-dim, by name and with a reason.** Its Alternatives line: *"384-dim (cheaper, meaningfully worse on technical text — Kang's corpus is technical)."* The spike recommends 384 precisely because quality was indistinguishable and resources were not. But "indistinguishable at n = 33" is not "equal", and the spike says so itself in its own caveat on that recommendation: *"this spike's own proxy is not powered to confirm or refute that on Kang's specific vault."* Overturning a documented architectural rejection requires evidence that contradicts it; evidence that cannot detect the effect in question is not that.

**Finding 3 — the resource argument is weaker than it looks, because DB-004 already paid it.** The spike measures 768-dim at 1.55 GB for 500,000 chunks. DB-004's own estimate: *"~1.5 GB at the 10-year 500k-chunk ceiling — trivial."* The architecture did not merely tolerate this cost, it budgeted for it and called it trivial. The re-embed throughput difference (10.07 vs 1.24 chunks/s, so roughly 14 hours against 112 hours for a full corpus re-embed) is real, but it is the cost of a **model change**, which DB-004's dual-index protocol already designs as a background, hot-rows-first, non-blocking migration. Optimising the architecture's committed dimension away to save a cost the architecture already accepted is the wrong trade.

**Finding 4 — the spike's largest measurement is not about the model at all, and must not be mis-read.** Every dimension tested exceeds 07 Part XIV's < 250 ms hybrid-candidate-fetch budget — 384-dim is already over at 100,000 rows, and at the 10-year ceiling every dimension is 6–17× over. This is measured, and the 500k extrapolations are calibrated against a real 384-dim measurement rather than assumed linear. 03_ROADMAP §8's RESERVED registry contains the row *"Vector DB server | sqlite-vec measurably failing at Kang-scale"*, and a reader could reasonably think this is that trigger. **It is not**, for reasons D5 sets out — and saying so is most of why this ADR exists rather than just naming a model.

**Finding 5 — this ADR activates a capability the repository's own registry marks RESERVED, and D2 as first drafted did not say so.** The claim traces to `docs/adr/038-model-router-taskspec.md:74` (accepted): *"Today, with no Ollama adapter built (Phase 5, RESERVED — 03_ROADMAP §8), that chain is empty by construction for every task class."* `config/defaults/providers.toml:17-18` carries the same claim, verbatim from that ADR's own implementing commit (`ac1c681`, 2026-09-14): *"No chain for task_class = "private": no local_only provider exists yet (Ollama's adapter is Phase 5, RESERVED — 03_ROADMAP §8)."* Its `[task_class.embedding]` entry, `providers.toml:39`, carries the same claim: *"chain = []  # no embedding provider wired yet — RESERVED, its own trigger."* `src/kang/adapters/ollama/__init__.py:4` agrees: *"Constitutional home: 04_ARCHITECTURE D010 (built at Phase 5 local-model migration)."* `14_CLAUDE.md:60` is unambiguous about what that means for an AI contributor drafting an ADR: *"Activate anything in the RESERVED registry (03_ROADMAP §8) — triggers fire via ADR, never via commit message."* D2 wires exactly this adapter, for a real embedding call, and had not named that as a RESERVED activation.

Checked against 03_ROADMAP §8's own table directly (`docs/03_ROADMAP.md:148-195`): **there is no row naming an "Ollama adapter."** The section `providers.toml` cites exists, but nothing inside it matches the claim. The nearest row, `:162` — *"Local-model migration per task class | Routing benchmarks showing parity per class | D010"* — cannot be the trigger for `embedding`: it describes a task class that currently runs on a cloud provider, proving local parity before switching, which is exactly Phase 5's own stated objective (`03_ROADMAP.md:117`: *"local models (the `private`/`routine` classes migrate local as quality permits — config drift, measured by the routing benchmarks)"* — `embedding` is not named there; only `private`/`routine` are). `embedding` never had a cloud chain to migrate from. D010's own diagram (`04_ARCHITECTURE.md:473-474`) draws `class: private` to *"Local LLM (Ollama)"* and `class: embedding` to *"Embedding model (local-preferred)"* as two separate arrows, together, on day one — not one arrow that later forks. And Phase 2's own objectives (`03_ROADMAP.md:51`) name *"semantic layer (embeddings + FTS + hybrid scoring)"* as **this** phase's required work, not Phase 5's.

**So the RESERVED marking on `providers.toml`'s `[task_class.embedding]` entry and on the Ollama adapter's own docstring is broader than anything that actually gates it.** It is correct for `private`/`routine` — those classes are genuinely mid-migration and the parity trigger genuinely has not fired. It is not correct for `embedding`, which D010 never routed through a migration trigger at all. The claim originates in ADR-038:74 and repeats in these two files, in the repository's own words, and D7 corrects the two files with dated corrections and appends a dated note beside ADR-038's own D4 text, rather than leaving the contradiction for the next reader to trip over.

**What is settled and not re-opened:** DB-004's `embedding_version` protocol, the per-version `vec_*` tables, and the dual-index migration (untouched — this ADR fills in `ver = 1`); 06 §5.3's chunk shape; that embeddings are local-preferred (D010) and that no vault content goes to a cloud embedding API, which the spike honored without needing to ask.

## Options

### Option 1 — Which model and dimension

**1A — `all-MiniLM-L6-v2`, 384-dim (the spike's own recommendation).** *For:* fastest by 4.5×, smallest index (782 MB), lowest latency of anything tested, and no measured quality penalty. *Against:* it requires overturning DB-004's explicit, reasoned rejection of 384-dim on evidence the spike itself says cannot test that claim (Finding 2); it is the most English-only, general-domain, smallest-capacity candidate, which is the worst position for a corpus whose code-switching the spike flags as present but unmeasured (its §1, limit 5, and §7); and it saves a resource cost the architecture already budgeted and called trivial (Finding 3). Declining a spike's recommendation needs a reason, and these are the three.

**1B — `nomic-embed-text`, 768-dim, via Ollama. (Recommended.)** *For:* it keeps DB-004's committed dimension, so `embedding_version` starts at the shape the whole schema was designed around and no amendment is needed; it runs on Ollama, so 17 §9 is honored and KANG gains no ML dependency (Finding 1); its quality is mid-pack and statistically identical to every other candidate (MRR 0.783, recall@5 0.879); its measured index size lands on DB-004's own estimate. *Against:* 1.24 chunks/s is slow — a full 500k re-embed is roughly 112 hours of background work, which is a real cost at any future model change, and it is 8× slower than 1A on that axis. And it is not a multilingual model, which leaves the code-switching risk the spike flags (§1, limit 5, and §7) unaddressed (D4 names it with a trigger rather than pretending otherwise).

**1C — `bge-m3`, 1024-dim, via Ollama.** *For:* the best point estimates on every quality column (MRR 0.822, recall@5 0.909) and genuinely multilingual, which is the one axis where the vault is unusual. *Against:* the advantage is inside the noise (Context: the 12.2pp spread across all candidates sits inside the ±15pp 95% confidence interval), and it pays the worst price on every measured resource axis — slowest to embed (0.44 chunks/s, ~315 hours for a full re-embed), largest index (2.07 GB), worst latency (4.1 s extrapolated). Adopting the most expensive option on an advantage the measurement cannot confirm inverts the burden of proof. The spike recommends against it for the same reason.

**1D — `multilingual-e5-base`, 768-dim.** *For:* the multilingual axis at DB-004's committed dimension — on paper the best fit for the vault's actual text. *Against:* it ran via sentence-transformers, so adopting it means PyTorch inside KANG's environment for a job Ollama already does (Finding 1). If this model later appears in Ollama's own library, that objection disappears and it becomes the strongest candidate — recorded in D4 as the named re-visit.

### Option 2 — Whether to decide at all now

**2A — Defer until the vault is larger and the benchmark can distinguish candidates.** *For:* the honest reading of the evidence is that no quality distinction exists yet. *Against:* the entire retrieval half of Phase 2 blocks on `embedding_version` having a row; DB-004's protocol exists precisely so that a first choice is *revisable* rather than final; and waiting does not obviously converge, since the vault grows slowly and the proxy's weakness is methodological as much as statistical.

**2B — Decide now on the settled constraints, with an explicit re-benchmark trigger. (Recommended.)** *For:* unblocks the phase; the dual-index protocol makes this cheap to reverse; and it puts the decision where the evidence actually is (dependency posture and the architecture's own commitments) rather than pretending the quality numbers carry it. *Against:* the choice rests on architectural fit rather than measured retrieval quality, which must be stated plainly in the ADR and in DB-004's note rather than implied to be benchmark-backed.

### Option 3 — How to resolve the RESERVED-registry gap (Finding 5)

**3A — Add a new 03 §8 row for "Ollama adapter", and fire it in this ADR.** *For:* follows `14_CLAUDE.md:60` most literally — a registry row, then an ADR firing it, is the documented shape for activating a RESERVED capability. *Against:* it would register a capability as having been RESERVED-then-fired when Finding 5's own evidence says `embedding` was never actually gated by any real trigger — D010 drew it straight to a local-preferred provider from inception. Adding a row only to fire it in the same document records a decision that was never genuinely pending, and leaves a permanent, misleading trace suggesting "Ollama for embeddings" needed a trigger to fire when it did not.

**3B — Narrow the RESERVED wording to what it actually gates, and say so with dated corrections. (Recommended.)** *For:* this is what Finding 5 actually found — not a capability ready to activate, but ADR-038:74, where the claim originated, and two files repeating it (`providers.toml`'s header, the Ollama adapter's own docstring) stating the RESERVED gate more broadly than 03 §8's own table supports, conflating `embedding` (never gated) with `private`/`routine` (genuinely gated, genuinely still RESERVED). Corrects the actual error rather than manufacturing a registry event to justify it — the same "the hole is in the specification" shape ADR-052 used for 06 §4.2's flowchart. *Against:* this ADR now edits two files outside its original D1 scope (a docstring and a comment) rather than only the one line it first touched, and appends a dated note to an accepted ADR — a wider footprint, though each change is a one-line dated correction, not a rewrite (matching this project's own precedent: ADR-039 correcting ADR-038 D3, ADR-052 correcting 06 §4.2).

**3C — Leave the RESERVED wording untouched and proceed anyway.** *For:* smallest possible diff. *Against:* this is the option that produced Finding 5 in the first place. Proceeding without correcting a documented RESERVED gate — when the repository's own rule (`14_CLAUDE.md:60`) requires activation to happen by ADR, not by commit — leaves the contradiction live for the next reader and the next contributor to trip over again. Declined.

## Decision

### D1 — `nomic-embed-text`, 768 dimensions, float32, as `embedding_version.ver = 1` (Option 1B)

Registered as version 1 in DB-004's existing `embedding_version` table, with its `vec_memory_v1` / `vec_episode_v1` / `vec_chunk_v1` tables at `float[768]`. The protocol is untouched; this fills in its first row.

### D2 — Ollama is the embedding runtime; no ML stack enters KANG's dependencies

The model is reached over Ollama's local HTTP API, as D010's `embedding` task class. **The port that carries that call is not decided by this ADR:** `ModelProvider.call` (`src/kang/domain/ports/model_provider.py:128`) returns a `ModelResult` (`:61-76`: `text`, `structured`, `tokens_in`, `tokens_out`, `cost_usd`, `latency_ms`) — no field can carry a vector. Whether embeddings reach Ollama through a new method on `ModelProvider`, a separate embedding port, and whether that call still runs through the Router and is logged to `model_call` (ADR-038 D4), is the embeddings slice's own decision — named here and left to it, the same deferral D5 makes for the hybrid fetch's shape. No `sentence-transformers`, no `torch`, no model weights under `%KANG_HOME%` — 17 §9's ruling applied exactly as written. This is what removes 1D and `bge-base-en-v1.5` from contention, and it is a firmer constraint than any quality number the spike produced.

**Consequence stated plainly:** KANG now has a real runtime prerequisite for embeddings that it does not itself install. A missing Ollama is a degraded-mode condition (A9), not a crash, and the retrieval slice owns that failure path — named here, not built here.

### D3 — The spike's own recommendation is declined, and the reasons are recorded

The spike recommended 384-dim on resource grounds. That recommendation is not adopted, for the three reasons in Findings 2 and 3: it would overturn a documented architectural rejection using evidence that cannot test it; it optimises away a cost DB-004 explicitly budgeted and called trivial; and it is the weakest-positioned candidate on the one corpus property the spike itself flags as unusual. **The spike was right to recommend it on the axes it could measure, and right to say its quality columns are not a ranking — this ADR simply weights the unmeasurable axes, which is the architect session's job and not the spike's.** Recorded rather than silently diverging, because a future reader comparing the two documents deserves to find the disagreement explained.

### D4 — The multilingual risk is named, with a trigger

The vault contains code-switched, non-English and shorthand-heavy text. `nomic-embed-text` is not a multilingual model, and this ADR chooses it anyway, for D1/D2's reasons. **Trigger for re-benchmark:** either (a) `multilingual-e5-base` or an equivalent multilingual model becomes available in Ollama's own library, removing D2's objection to 1D entirely, or (b) retrieval quality is observably poor in practice on code-switched or shorthand-heavy notes once the memory browser's search exists to notice it. Either fires a re-run of the spike's method at the vault's then-current size, and DB-004's dual-index protocol is what makes acting on it a background migration rather than a rewrite.

### D5 — The `sqlite-vec` latency finding: the RESERVED trigger has **not** fired

03_ROADMAP §8's *"Vector DB server | sqlite-vec measurably failing at Kang-scale"* is not satisfied by the spike's measurement, and 03 §8's row gets a dated note saying so. Two things stand between the measurement and that conclusion, and neither was tested:

1. **It measured `vec0`'s default exact brute-force mode, unfiltered, over the full 500,000-row ceiling.** `sqlite-vec` documents other modes — quantized vector types and partition/metadata filtering — that change scan cost by large factors. This ADR does not assert their performance (the library is not installed in the drafting session and no number here is invented); it asserts only that **an untested mode cannot be the basis for declaring the technology failed.**
2. **The query shape itself is undecided.** 07 Part XIV's budget line reads *"vec k=64 + FTS k=64 + prefilter"*, which is the independent-halves shape the spike measured. 06 §5.2 weights lexical BM25 at 0.20 alongside semantic at 0.40, and the FTS half already measures well inside budget at 10-year scale (ADR-049's nightly suite). A pipeline that generates candidates with FTS and uses vectors only to *re-rank* them performs on the order of 64 vector comparisons rather than 500,000. That is a standard design, and choosing between the two shapes is the **retrieval slice's** decision, not this one's.

**So the finding is real, load-bearing, and correctly escalated by the spike — and it is a question about the retrieval pipeline's shape before it is a question about the storage technology.** Deciding the shape here, before the slice that owns it exists, is the mistake that produced the gate's own holes (ADR-052). It is carried forward as the retrieval slice's first named input.

**Dated note (2026-10-06).** Decided by ADR-056 D1: independent halves with exact vectors for memory records, measured inside budget on the year-10 corpus (217–239 ms against 250 ms), with `int8` (~90 ms, measured) as the named remedy and its trigger. Vault chunks remain their own slice's question.

### D6 — What this ADR does not do

No code, no migration, no `embedding_version` row inserted (that is the embeddings slice). No change to DB-004's protocol, the chunk shape, the scorer weights, or 07 Part XIV's budget numbers. No decision on the hybrid fetch's shape (D5). No decision on which port carries the embedding call (D2) — a new `ModelProvider` method, a separate embedding port, and whether it runs through the Router's `model_call` ledger are the embeddings slice's own ADR to make, the same way D5 defers the hybrid fetch's shape to the retrieval slice. No second spike commissioned — if one is wanted for the latency question, that is Kang's call and its own brief.

### D7 — The RESERVED marking was mis-scoped, not activated; corrected, and only for `embedding` (Option 3B)

`config/defaults/providers.toml:17-18`'s comment sentence is scoped to `task_class = "private"` — but the claim inside it, the parenthetical "(Ollama's adapter is Phase 5, RESERVED — 03_ROADMAP §8)", states that as a fact about the adapter itself, unqualified by task class when read alone. `src/kang/adapters/ollama/__init__.py:4` and `docs/adr/038-model-router-taskspec.md:74` (the claim's origin, Finding 5) carry the same claim with no task-class scoping at all. That is correct for `task_class.private` and `task_class.routine` — 03_ROADMAP's own Phase 5 objective (`:117`) and RESERVED row (`:162`, "Local-model migration per task class | Routing benchmarks showing parity per class") genuinely have not fired for either, and D1/D2 do not touch them. It is not correct for `task_class.embedding`: D010 (`04_ARCHITECTURE.md:473-474`) routed `embedding` to a local-preferred provider from the decision's own inception, never through a cloud chain a migration-parity trigger could apply to, and 03_ROADMAP's Phase 2 objectives (`:51`) require the semantic layer this phase, not Phase 5. There is no row in 03 §8 naming an "Ollama adapter" capability, and Option 3A's alternative — inventing one only to immediately fire it — would misrecord something that was never actually gated.

**This ADR corrects the RESERVED wording rather than firing a trigger, because Finding 5 found a documentation gap, not a pending capability.** Dated corrections land on:

- `config/defaults/providers.toml`'s header comment (narrowing "Ollama's adapter is Phase 5, RESERVED" to name `private`/`routine` specifically) and its `[task_class.embedding]` comment (removing "RESERVED, its own trigger" — D1/D2 are this class's own resolution, not a fired trigger);
- `src/kang/adapters/ollama/__init__.py`'s own docstring (the same narrowing — it is the file `14_CLAUDE.md:60` would otherwise call a RESERVED activation);
- `03_ROADMAP.md:162`'s "Local-model migration per task class" row (a dated note stating its trigger has never applied to `embedding`, which D010 never gated behind it — this ADR's use of Ollama for embeddings is not that trigger firing);
- `docs/adr/038-model-router-taskspec.md:74` — accepted, never rewritten; a dated note appended beside its D4 text, following ADR-038 D3's own "Corrected by ADR-039" pattern, narrowing "Phase 5, RESERVED" to `private`/`routine` and pointing to this D7.

**What this explicitly does NOT activate:** the Ollama adapter gains no code beyond what the embeddings slice needs to reach it for `task_class.embedding` calls (D1/D2's own scope, unchanged). `task_class.private` and `task_class.routine` remain exactly as RESERVED as before this ADR, gated on the same unfired routing-benchmark-parity trigger — nothing here authorizes wiring a local chat/completion path through Ollama. A future ADR doing that still owes its own justification against that row's own trigger, on its own evidence.

## Consequences

**What becomes possible.** 04 §20.1's oldest open question closes, and the embeddings slice has a concrete model, dimension, and runtime to build against. DB-004's 768 default stops being an assumption and becomes a confirmed-by-measurement figure for index size, with its own estimate independently corroborated to within a few percent.

**What becomes harder, or costs something.** KANG acquires an external runtime prerequisite it does not install, so "embeddings unavailable" becomes a real degraded state the retrieval slice must handle. A future model change costs roughly 112 hours of background re-embedding at the 10-year ceiling — designed-for by DB-004's protocol, but a real number worth knowing before choosing to change models casually. The multilingual risk is accepted rather than mitigated, with a trigger. And the choice rests on architectural fit rather than measured quality, which is an honest weakness: if the vault grows and a re-run finds a real quality gap, this decision was made on the wrong axis and should be revisited without embarrassment — which is exactly what `embedding_version` exists for. The RESERVED registry now carries a scope distinction that is per-task-class, not per-adapter-file (D7) — a future contributor skimming `providers.toml`'s header alone, without also finding D7, could still read the Ollama adapter as blanket-reserved. Worth a clearer registry convention (naming task classes, not just adapters, in a RESERVED row) if a second shared-adapter, multi-task-class runtime produces the same gap.

**A standing caution for whoever reads the spike next.** Its headline resource numbers are sound and its quality numbers are explicitly not a ranking. Anyone citing "all-MiniLM won the benchmark" would be citing something the spike took care not to say.

**Named, not decided:** the hybrid fetch's shape and the latency budget's reachability (retrieval slice, D5); which port carries the embedding call — a new `ModelProvider` method or a separate embedding port, and whether it runs through the Router's `model_call` ledger (embeddings slice, D2); whether a follow-up spike on `sqlite-vec`'s quantized and partitioned modes is worth commissioning; the degraded-mode behavior when Ollama is absent; `gte-base`'s non-completion, which may be machine-specific and is not a finding about the model.
