## Context

Phase 2 ("The Memory") has not started. Confirmed against the real repository on 2026-09-17, not assumed from the documents: migrations `0001`–`0019` create no `memory_record`, `memory_revision`, `memory_candidate_queue`, `episode`, `link`, `link_index`, `vault_note`, `vault_chunk`, `embedding_version`, `fts_*`, or `vec_*` table (the only mention of `memory_record` anywhere under `migrations/` is a comment in `0001_initial.sql`'s `tombstone` DDL naming it as a future entity). `domain/memory/`, `kernel/context/`, `domain/vault/`, and `adapters/obsidian/` are empty `__init__.py` stubs whose docstrings cite 06_MEMORY and "built at Phase 2 — 18 §4". `config/defaults/` holds `kang.toml`, `permissions.toml`, `providers.toml` — no `memory.toml` (ADR-047 D2 already names its first consumer). `tools/` has no corpus generator; `tests/fixtures/` has no synthetic corpus. The one memory-adjacent thing that is real: `kernel/permissions/pairing.py` already lints `memory.propose:rule|profile` as ungrantable and `web.fetch × memory.read:sensitive` as a forbidden pairing (05 §8, built at M3 "so it is there before the first grant that would violate it").

`07_DATABASE.md` already *wrote* the schema. 18 §7.2 is the reason this ADR comes first: "Memory is **policy over a store**, not a store... Schema-bearing truth precedes every policy that governs it." The gate (06 Part IV), the lifecycle function (M-002), the corpus generator, and every later slice emit into or read from these tables. This ADR's job is not to design a schema — it is to land 07's schema as one migration and to name, in daylight, the places where 07's own text does not decide, or decides two ways. Four such places were found while grounding this against the real DDL and the real SQLite on this machine:

**Finding 1 — 07 §5.1 gives a candidate two homes.** `memory_record.status` is declared `DEFAULT 'candidate'` with `'candidate'` and `'rejected'` in its CHECK enum — which says a candidate is a `memory_record` row. Twelve lines later, `memory_candidate_queue` carries `payload TEXT NOT NULL -- full proposed record as JSON` plus `flags`, `flag_context`, `expires_at`, `resolved` — which says a candidate is a queue row, and the payload would be a duplicate of the record if both existed. 06 §2.1D says both things in one sentence: "a lifecycle **status**... Candidates live in a quarantine table." 07 §1.4 principle 1 (one authoritative home per datum, AR6) forbids the literal reading of the DDL as written. The gate cannot be built until one home is chosen; this is Option 1 below.

**Finding 2 — the derived indexes key on rowids that SQLite does not promise to keep.** 07 §6.1's `fts_memory` is an FTS5 external-content table with `content_rowid='rowid'`; §6.2's `vec_memory` keys on `record_rowid INTEGER PRIMARY KEY`. Both therefore bind a derived row to the *implicit* rowid of a table whose declared primary key is `id TEXT` (DB-003). SQLite's own VACUUM documentation states that VACUUM "may change the ROWIDs of entries in any tables that do not have an explicit INTEGER PRIMARY KEY." Probed on this machine while drafting (Python 3.12.5, SQLite 3.45.3, a throwaway file, 2026-09-17): after deleting rows and running `VACUUM`, and separately `VACUUM INTO` (07 Part XII's only sanctioned backup method), the surviving implicit rowids were *not* renumbered, and the FTS join still resolved correctly. That is observed behavior on one version, against a documented reservation. A ten-year system whose SQLite version will change several times cannot key its retrieval indexes on behavior the documentation explicitly declines to guarantee. `message` (migration `0019`, one day old) has the same shape and is the fourth table Kang's 2026-09-17 ruling puts under FTS5 (below). This is Option 2.

**Finding 3 — the migration's scope is not fixed anywhere.** 18 §4 says "store schema for memory/episodes/queue"; 07 §6.1 says the four `fts_*` tables are "identical pattern"; and Kang ruled in conversation on 2026-09-17 (recorded in the vault's Build State note; if this ADR is accepted it becomes that ruling's repository record, per 14 §14.5 — decisions live in ADRs, not vault notes) that `fts_message` is built *together with* its three siblings when Phase 2 memory work starts, so it is never a one-off shape the others must later match. `fts_chunk` needs `vault_chunk`; `vault_chunk` needs `vault_note`; `embedding_ver` columns need `embedding_version` to exist or every insert fails (ADR-038's own empirically confirmed lesson); `vec_*` tables need a dimension that only the embedding-model spike (18 step 21, 04 §20.1) can supply. What lands in one migration, and what deliberately does not, is Option 3.

**Finding 4 — 18 §4's own order cannot be read literally.** It lists "synthetic corpus generator **first**... then store schema." A generator that emits rows needs tables to emit into. The honest reading, recorded here so the next session does not re-derive it: the corpus generator is first among *behavioral* components and precedes the gate (the first policy); the schema is truth, not behavior, and precedes the generator that fills it — which is 18 §7.2's own sentence applied one step earlier. The slicing plan this ADR opens places the generator immediately after this migration.

**What is settled and not re-decided here:** the type taxonomy (M-001), the state machine (M-002), the gate (M-003 — nothing in this ADR creates or weakens a write path; no code that writes these tables exists after it), every column and CHECK in 07 §5.1/§5.3/§5.4 except where a finding above forces a named deviation, UUIDv7 TEXT identity (DB-003), the sync quartet on synchronizable rows (D009), tombstones (already migrated in `0001`), FTS5 external-content mode and the three trigger duties (07 §4.1/§6.1), 768-dim/versioned embeddings (DB-004 — parameterized, not landed), app-level encryption of `private` content (DB-005 — the invariant lands as a CHECK; the mechanism is a later slice).

## Options

### Option 1 — Where a candidate lives

**1A — A candidate is a `memory_record` row with `status='candidate'`; `memory_candidate_queue` becomes a gate-metadata sidecar (flags, expiry, resolution) keyed to it, its `payload` column dropped.**
- *For:* 06 M-002's diagram is literally one status column; `memory_revision` covers edit-then-approve as revision 2; one store-layer transition function covers admission and lifecycle alike.
- *Against:* quarantine becomes a filter every reader must remember (`status='active'` in default mode, and additionally `≠ candidate, ≠ rejected` in deep mode, which 06 Part X says includes archived and superseded) — a forgotten filter leaks an unapproved AI proposal into an agent's context, which is the exact failure M-003 exists to make structurally impossible, and 13 §2.8 wants it provable as "no code path," not "every path filters." The FTS/vec sync triggers gain a status condition on top of the `private` condition. The gate's near-duplicate probe needs the candidate's embedding, which under 1A would sit in `vec_memory` beside real records and force every kNN to join-filter status. Candidate rows carry the sync quartet and change-capture, so an unapproved proposal replicates as truth-shaped rows; and a rejected candidate's 30-day purge is a `memory_record` DELETE, which fires the delete-capture trigger and (per 07 §5.1) a `tombstone` for a thing that was never a memory.

**1B — A candidate lives only in `memory_candidate_queue`; `memory_record` holds gate-passed records only; the queue row's `id` is the UUIDv7 that becomes the record's `id` on approval. (Recommended.)**
- *For:* quarantine is physical — 12_API §10's sentence becomes literally true at the table level ("the API physically has no operation that writes an active memory except `memory.approve` of an existing candidate... or Kang-principal explicit saves"), and 13 §2.8's "no code path" claim is provable by construction. Every `memory_record` row is index-eligible unless `private`, so the FTS/vec triggers stay one condition. The queue already has no sync quartet in 07's own DDL — the ADR-005 shape (operational rows that never replicate), and what *does* replicate is the approved product, which does carry the quartet. Candidate/rejected purge is queue maintenance: no capture, no tombstone. One identity flows through the lifecycle ("why was this rejected?" and the audit trail correlate on the same id that would have become the record).
- *Against:* `memory_record.status`'s written CHECK loses `'candidate'` and `'rejected'` — a dated amendment to 07 §5.1, the same shape ADR-046 used for `conversation`/`message`. 06 M-002's first transition becomes a table move rather than a status flip; admission (Part IV) and lifecycle (Part III) become two store-layer functions, which is how 06 already separates them in prose. An edit before approval is recorded in the queue's `resolved='edited'` plus the gate's audit entry (06 §12.3), and `memory_revision` history begins at revision 1 on approval — 06 §8.2's "edits never overwrite silently" concerns active records and is untouched.

### Option 2 — How the FTS5 and vec0 indexes key their content rows

**2A — Keep 07's DDL as written (implicit rowid on `id TEXT PRIMARY KEY` tables) and make a rebuild of every derived index mandatory after any restore from snapshot and after any VACUUM.**
- *For:* zero deviation from the written DDL; the four FTS tables land exactly as 07 shows them; on the SQLite version probed, nothing renumbers today.
- *Against:* it converts a documented non-guarantee into an operational rule that must be remembered forever, in two places (07 Part XV.1's restore procedure; Part XVII's "suggest offline VACUUM" line), by code that does not exist yet (`kang rebuild-indexes` — a full rebuild is budgeted at < 15 min on the 10-year corpus, 07 Part XIV). The failure when it is forgotten is *silent*: FTS hits and kNN neighbors point at the wrong records, which is the "wrong memories" outcome 06 Part XIV's meta-rule forbids ("never toward silent corruption"). It is also the un-boring choice: SQLite's own FTS5 external-content documentation models the content table with an `INTEGER PRIMARY KEY`.

**2B — The four FTS-indexed tables (`memory_record`, `episode`, `vault_chunk`, `message`) carry an explicit `rowid INTEGER PRIMARY KEY` alias; `id TEXT NOT NULL UNIQUE` stays the identity everywhere outside the store. (Recommended.)**
- *For:* the rowid is now guaranteed stable by SQLite's contract, not by observed behavior; FTS5's `content_rowid='rowid'` and vec0's `record_rowid` bind to something that cannot move. Verified on this machine while drafting: a declared `rowid INTEGER PRIMARY KEY` column is accepted, `SELECT rowid` returns it, a foreign key to the `UNIQUE` text column is enforced (`memory_revision.record_id → memory_record(id)` and every `link` endpoint keep working unchanged), and an external-content FTS5 table keyed on it resolves correctly. Nothing outside `adapters/sqlite/` ever sees the integer: no port datatype, no API resource, no event payload, no `change_log` row (which captures `entity_id = NEW.id`, the UUID), no sync change-set. `WITHOUT ROWID` is deliberately not used anywhere here — it would remove the very rowid FTS5 requires.
- *Against:* a real deviation from 07's DDL on four tables and from DB-003's letter ("primary key is a UUIDv7"), argued and dated rather than silently matched. `message` (migration `0019`) must be rebuilt (new table, order-preserving copy, drop, rename — the `0005`/`0016` pattern, ADR-024): cheap now, brutal after a year of transcripts — D009's own "cheap now, impossible to retrofit later" argument, applied to a table that is one day old. Two identifiers per row in `sqlite3 kang.db` output, which costs a little of 07 §1.4's inspectability — the UUID column is still the one every human and every other table uses.

### Option 3 — What one migration lands

**3A — Only the memory trio and episodes (`memory_record`, `memory_revision`, `memory_candidate_queue`, `episode`), the literal reading of 18 §4's "memory/episodes/queue"; links, vault, FTS, and `embedding_version` each land with their own later slice.**
- *For:* the smallest possible first migration.
- *Against:* `embedding_ver INTEGER REFERENCES embedding_version(ver)` cannot be written without its parent table (ADR-038's lesson), so the trio would land without the column and a later migration would rebuild every table to add it; `fts_memory` and `fts_episode` would land later than their content tables, so every row inserted before then needs a rebuild step every later slice inherits; and the four FTS tables would land in at least three different migrations — the one-off-shape drift Kang's 2026-09-17 ruling exists to prevent. The `link` table is needed by the gate (proposals carry `links[]`, 06 §4.2; approval resolves `derived_from`/`supersedes`), so it would be the very next migration anyway.

**3B — The whole memory-truth DDL in one migration: 07 §5.1, §5.3, §5.4, `embedding_version` (Part VIII), the four `fts_*` tables with their sync triggers (§6.1), change-capture triggers for the synchronizable tables, and the `message` rebuild — with `vec_*`, secondary indexes, and views explicitly not landed. (Recommended.)**
- *For:* one migration, one pattern, every CHECK enum from 06's taxonomy enforced at once (07 Part XVI's "enum exhaustiveness" suite has one target); the FTS sync triggers exist before the first row is ever inserted, so no slice ever inherits a rebuild; `embedding_version` and the columns that reference it land together; `link`/`link_index`/`vault_note`/`vault_chunk` are DDL only — empty until their slices, exactly as `project`/`competition`/`goal` sat empty from `0006` until ADR-013–016 gave them write paths. What is left out is left out for a stated reason each (D4).
- *Against:* a large migration file (DDL only — no data transform, so the Python-companion rule of 07 Part XIII.1 is not triggered) and a large schema test suite in the same PR. Accepted: the suite is the deliverable 07 Part XVI names; deferring it does not shrink it.

## Decision

### D1 — A candidate lives only in `memory_candidate_queue` (Option 1B)

`memory_record.status`'s CHECK becomes `('active','under_review','superseded','archived')`; the `DEFAULT 'candidate'` is removed (the gate supplies `'active'` explicitly at approval — there is no default that could accidentally admit). The comment `-- deleted = row gone + tombstone` stays. `memory_candidate_queue` lands exactly as 07 §5.1 writes it (`id`, `payload`, `flags`, `flag_context`, `proposed_at`, `expires_at`, `resolved`, `resolved_at`), no quartet, no capture trigger — and the gate slice's contract, fixed here so it is not re-decided there: the queue row's `id` is minted as a UUIDv7 at proposal time and is the `id` the `memory_record` row receives on approval, so one identity threads proposal → queue → record → audit. A rejected or expired row is purged by the janitor after 30 days (06 §7.1) as a plain queue delete — no tombstone, because it was never a synchronizable row. 06 §2.1D and M-002 receive a dated clarifying note: `candidate` and `rejected` are real states of the lifecycle and live in the quarantine table; the record table holds gate-passed records only. `episode` has no candidate state in 07's DDL (`active | compressed | archived`) and gains none — episodes are written by registered rules or Kang (06 §4.1) and never queue; the gate still validates their provenance.

### D2 — Explicit `rowid INTEGER PRIMARY KEY` on the four FTS-indexed tables (Option 2B)

`memory_record`, `episode`, `vault_chunk`, and `message` are declared with `rowid INTEGER PRIMARY KEY` as their first column and `id TEXT NOT NULL UNIQUE` as their identity (for `vault_chunk`, `id` is already the identity 07 writes; its `UNIQUE (note_path, seq)` stays). Every foreign key in the schema continues to reference `id`. Every port datatype, API representation, event payload, `change_log.entity_id`, and tombstone continues to carry the UUIDv7 only — the integer never crosses the `adapters/sqlite/` boundary, and a store test proves no port dataclass exposes it. `message` is rebuilt in this migration by the `0016` pattern (an order-preserving `INSERT ... SELECT`, regardless of row count, then drop and rename); `idx_message_conversation_at` is recreated. DB-003 gets a dated clarification beside its own decision text: *identity* is the UUIDv7; the four text-indexed tables additionally carry a storage-local integer rowid alias that exists for FTS5/vec0 binding stability and nothing else. Tables nothing keys on by rowid (`memory_revision`, `memory_candidate_queue`, `link`, `link_index`, `vault_note`, `embedding_version`) land exactly as 07 writes them.

### D3 — One migration (Option 3B): the DDL that lands

Migration `0020` (the next free number at drafting time — re-verified at write time, not assumed) lands:

- **§5.1:** `memory_record` (D1's CHECK, D2's rowid, and the DB-005 invariant expressed literally as a CHECK: `sensitivity <> 'private' OR (content = '[encrypted]' AND content_enc IS NOT NULL)` — 07's forward invariant only; the reverse is not in 07 and is not added), `memory_revision` (CASCADE per Appendix B), `memory_candidate_queue`, `episode` (D2's rowid; `compressed_into` self-reference as written).
- **§5.3:** `vault_note`, `vault_chunk` (D2's rowid; CASCADE per Appendix B). Empty until the Obsidian slice; DDL lands now so `fts_chunk` can.
- **§5.4:** `link` (the 13-value type CHECK from 06 §9.1 verbatim; the `UNIQUE (src_kind, src_id, dst_kind, dst_id, type)`), `link_index` (`WITHOUT ROWID`, as written — nothing keys on its rowid).
- **Part VIII:** `embedding_version`, empty; `embedding_ver` on `memory_record`/`episode`/`vault_chunk` becomes a real `REFERENCES embedding_version(ver)` because the parent now exists in the same migration.
- **§6.1:** `fts_memory`, `fts_episode`, `fts_chunk`, `fts_message` — external-content, `tokenize = 'porter unicode61'`, `content_rowid='rowid'` now binding to D2's explicit column — each with its three sync triggers (insert / update of `content` / delete). `fts_memory`'s triggers carry the `private` exclusion condition (`WHEN NEW.sensitivity <> 'private'`, and the matching delete-side handling on an update that flips sensitivity) so ciphertext is never indexed and plaintext of a private record never exists in the DB — 07 §6.1's rule made mechanical. The other three carry no condition: `episode`, `vault_chunk`, and `message` have no `sensitivity` column in 07.
- **§4.1 third duty:** change-capture triggers for the synchronizable tables — `memory_record`, `memory_revision` (insert only; revisions are append-only), `episode`, `link` — in `0001`'s established per-column shape. Not on `memory_candidate_queue`, `link_index`, `vault_note`, `vault_chunk`, `embedding_version`: operational or derived, never synchronized (07 Appendix A; ADR-005's reasoning).
- **The `message` rebuild** (D2).

### D4 — What this migration deliberately does not land, and why

- **`vec_memory` / `vec_episode` / `vec_chunk`:** DB-004 fixes the dimension "per embedding_version"; the embedding-model spike (18 step 21, 04 §20.1) has not run, so the dimension is a hypothesis, and vec0 itself needs the `sqlite-vec` extension — a new native dependency that lands with its E10 paragraph in the embeddings slice's own ADR (it is pre-approved *as a choice* by 04 D004/07 §1.3; its *arrival* still follows 11 §25). Verified while drafting that this Python's `sqlite3` module can enable extension loading (`enable_load_extension(True)` succeeds on Python 3.12.5), so the embeddings slice does not inherit an unknown.
- **Secondary indexes** (`idx_mem_type_stat`, `idx_mem_status`, `idx_episode_time`, `idx_linkindex_dst` from 07 Part VI): the index doctrine says every index cites its consumer and speculative indexes are forbidden; no consumer exists after this migration. They land with the gate, lifecycle, link, and retrieval slices respectively — the same rule `0001` applied to the Planner's P0 indexes ("arrive with their consumers").
- **Views** (`v_project_memory`, `v_contested_records`, 07 §4.1): same rule; ADR-032 already found none of 07's four views is a real `CREATE VIEW` today. They arrive with the domain-view (link) and lifecycle slices.
- **`config/defaults/memory.toml`:** its first real consumer is the gate (`[gate]`), per ADR-047 D2's own naming; a config file nothing reads is the "config that doesn't back anything yet" that ADR-047 declined to create.
- **Any store, port, fake, or operation:** this ADR lands truth and its schema suite only. The insert-only half of the store ports arrives with the corpus generator (the next slice), which is their first caller; the rest of each port grows method-by-method with its consumers, exactly as `ConversationStore` grew `purge_stale` and `list_recent` under ADR-047.
- **A `kang rebuild-indexes` surface:** under D2 the rowid-stability reason for it is gone; what remains is F6 (index corruption) and the health panel's "index parity" gap ADR-033 named — both belong to the janitor/health slice.

### D5 — Access statistics are operational, not truth: no change capture, no revision bump

07 §5.1 places `last_accessed` and `access_count` on `memory_record`. A retrieval that touched them on every read would write to a synchronizable truth row per assembly — and cannot, because retrieval runs on DB-001's read-only pool (`query_only = ON`, ADR-036 D3), so those columns can only ever be maintained by a scheduled writer (the janitor's "recompute importance from access stats," 06 §6.1, most plausibly derived from the record ids each `invocation.manifest` already lists). Fixed here at the DDL level so the gate and retrieval slices inherit it: the `memory_record` update-capture trigger is declared `AFTER UPDATE OF <every column except last_accessed, access_count>`, so a statistics-only touch emits no `change_log` row, and the store-layer optimistic-revision rule (0001: revision bumps ride the store's UPDATE, never a trigger) does not bump `revision` for a statistics-only write. Which component maintains the statistics, and from what source, is the janitor slice's decision, not this one's.

## Consequences

**What becomes possible:**
- Every later Phase 2 slice has a fixed, tested target. The corpus generator can emit; the gate can be written as pure policy over ports; 07 Part XVI's schema suite exists from the first memory table, so a taxonomy drift between 06 and the DDL is a red build from day one.
- M-003 gains a structural guarantee before a line of gate code exists: there is no table a candidate and an active record share, so "an AI proposal reached retrieval" requires a code path that *creates a `memory_record` row*, and 12_API §10 already fixes those to two (`memory.approve`, Kang-principal saves).
- The four FTS tables share one migration, one trigger shape, one rowid contract — Kang's 2026-09-17 ruling, now a repository decision rather than a vault note.
- `fts_message` exists, so the deep-search-over-chat-history item the Build State backlog names stops being blocked on "the first-ever FTS5 table."

**What becomes harder, or costs something:**
- **07_DATABASE needs three dated amendments** (D1's CHECK, D2's rowid on four tables, D5's trigger column list) and DB-003 a clarification, in the same PR as the migration (CLAUDE.md §6). The document gets slightly longer and slightly less uniform: four tables now look different from the rest. The alternative — DDL that silently disagrees with its own document — is the drift this project treats as a bug with an owner.
- **`message` is rebuilt one day after it was created.** A real cost in migration surface for a table with almost no rows; the cheapest moment to pay it, and the last cheap one.
- **The lifecycle is two store-layer functions, not one.** Admission (queue → record, the gate) and transition (record status changes, M-002) are separate seams. 06 M-002's "one store-layer function with exhaustive tests" now describes the transition function only; the gate has its own exhaustive suite (13 §2.8). Named so the gate slice does not try to reunify them.
- **A large first migration and a large schema suite** land together. There is no smaller honest unit: every table left out would return in the next migration with a `REFERENCES` it needs.
- **Nothing runs after this ADR.** No operation, no store, no UX. That is the same "dormant if the next slice slips" shape ADR-036 D3 and ADR-038 D1 chose deliberately — and the reason the slicing plan puts the corpus generator and the insert-only store ports immediately behind it.
- **Two identifiers on four tables** in raw `sqlite3` output. Accepted against 07 §1.4's inspectability: the UUID is still the only id a human, a port, or another table uses.

**Named, not decided here (each belongs to a later slice's ADR):** how registered rules are declared and authorized at the gate; the retirement of 04 D013's `memory.write:{types}` vocabulary in favor of 05 §8's `memory.propose:{types}`; the gate's semantic probes (cosine near-duplicate, NLI conflict) before an embedding provider exists; the embedding port's shape (ADR-038's `ModelProvider.call` returns text or a schema instance, never a vector — `task_class="embedding"` is routable to nothing today); which component maintains access statistics and from what source; where recipe files live; `episode.content`'s per-type JSON schemas; whether `episode` needs a `sensitivity` column (it has none, so a review episode cannot be `private` — a gap for the evening-review slice to look at, not paper over).
